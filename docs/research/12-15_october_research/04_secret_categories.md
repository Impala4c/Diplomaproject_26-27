# Девять категорий секретов: определения и границы

Названия сохранены из материалов команды. Это рабочая классификация проекта, а не общепринятый стандарт из девяти непересекающихся классов. Ниже приведены названия форматов и семейств, а не действующие значения, искусственные ключи или рейтинг распространённости. [P3](08_sources.md#p3)

## 1. API keys

**Смысл:** ключи для обращения к API; конфиденциальность определяется назначением и правилами провайдера, а не только названием поля.

**Подтверждённый пример семейства:** Stripe secret/restricted API keys. Stripe отличает их от publishable keys, которые допускается размещать в клиентском коде. [A07](08_sources.md#a07)

**Важное исключение:** API keys, используемые для Firebase services, обычно не требуют обращения как с секретами; документация отдельно оговаривает ключи для других Google Cloud API. Поэтому нельзя автоматически размечать любой `apiKey` как утечку. [A08](08_sources.md#a08)

**Решение для проекта:** учитывать провайдера, тип ключа и контекст использования. Не считать одного имени `api_key` достаточным основанием положительной метки.

## 2. Access tokens

**Смысл:** токены, используемые для авторизации доступа. В bearer-механизме владение токеном имеет значение для доступа к защищённому ресурсу; это не универсальное описание всех видов токенов. [A10](08_sources.md#a10)

**Примеры семейств из материалов команды:** personal access tokens, OAuth access tokens и токены приложений. В перечне GitHub generic patterns отдельно присутствует HTTP bearer authentication header. [P3](08_sources.md#p3) [S10](08_sources.md#s10)

**Решение для проекта:** искать значение токена вместе с признаками авторизации. Имя переменной или ссылка на переменную окружения сами по себе не являются опубликованным токеном. Название «access token» пересекается с категорией 8.

## 3. AWS credentials

**Смысл:** учётные данные AWS. Для access keys AWS описывает пару access key ID и secret access key. Структура временных STS credentials дополнительно содержит session token и время истечения. [A09](08_sources.md#a09)

**Примеры семейств:** IAM access keys и временные STS credentials. Поля для анализа: `AccessKeyId`, `SecretAccessKey`, `SessionToken`; это имена полей, не найденные значения.

**Решение для проекта:** различать обнаруженный идентификатор и наличие секретного компонента. Один access key ID не доказывает наличие полного комплекта для доступа. Связь нескольких компонентов сохранять как контекст, не выполнять AWS-запросы с ними. [A09](08_sources.md#a09) [P0](08_sources.md#p0)

## 4. Private keys

**Смысл:** закрытый ключевой материал в документированных форматах. Библиотека cryptography различает операции загрузки закрытых и открытых ключей, включая PEM и OpenSSH. [A14](08_sources.md#a14)

**Примеры семейств:** RSA/EC private keys, PKCS#8 private keys, OpenSSH private keys. Заголовок PEM — признак формата, не отдельный полноценный ключ.

**Решение для проекта:** анализировать весь блок, а не только строку заголовка. Открытый ключ не размечать как закрытый. Корректный разбор структуры не устанавливает использование ключа реальным сервисом. Заведомо лабораторное происхождение отмечать отдельно от типа материала.

## 5. Database credentials

**Смысл:** секретные компоненты данных подключения к базе, прежде всего пароль в связи с пользователем и сервером. PostgreSQL документирует отдельные параметры `user`, `password`, `host` и `dbname`. [A12](08_sources.md#a12)

**Подтверждённый пример:** пароль PostgreSQL в параметрах подключения. MySQL, MongoDB, Redis и SQL Server присутствуют в прежнем перечне команды, но этот этап не подтверждает, что у прототипа уже есть детектор каждого из них. [P3](08_sources.md#p3)

**Решение для проекта:** учитывать отношения между полями. Пользователь или hostname без секретного компонента не означают утечку database credentials в выбранной постановке. Не отбрасывать короткий пароль только из-за значения энтропии.

## 6. Passwords

**Смысл:** пароли, непосредственно включённые в программный артефакт; hard-coded password назван примером в CWE-798. [A01](08_sources.md#a01)

**Примеры из материалов команды:** пароль приложения, SMTP, параметры аутентификации и конфигурация автоматизации. Эти названия задают предполагаемый охват, а не подтверждают наличие утечек в конкретных репозиториях. [P3](08_sources.md#p3)

**Решение для проекта:** отличать строковое значение пароля от названия аргумента, сообщения интерфейса и чтения переменной окружения. Не считать `test` или `example` в пути автоматическим основанием метки `NON_SECRET`. Хеш пароля не тождественен паролю в открытом виде; его включение требует отдельного решения о границах.

## 7. Connection strings

**Смысл:** составные строки подключения, которые могут включать секретный компонент. В PostgreSQL URI пользователь и пароль являются необязательными составляющими; URI без пароля не доказывает раскрытия пароля. [A12](08_sources.md#a12)

**Примеры семейств:** PostgreSQL URI; GitHub также документирует generic pattern для MongoDB connection strings с credentials. [A12](08_sources.md#a12) [S10](08_sources.md#s10)

**Решение для проекта:** выделять и маскировать секретное поле, а не объявлять любой URL секретом. Один пароль внутри URI не должен искусственно увеличивать общий счёт как несколько независимых утечек из-за пересечения категорий 5, 6 и 7. Точный способ учёта нужно согласовать.

## 8. JWT / authentication tokens

**Смысл:** JWT — формат представления набора claims, который использует JWS или JWE. Само распознавание JWT не устанавливает назначение токена как credential. [A11](08_sources.md#a11)

**Примеры семейств:** JWT, используемый для аутентификации/авторизации; bearer token; session/refresh tokens из перечня команды. Не все bearer tokens являются JWT, и название категории объединяет разные механизмы. [A10](08_sources.md#a10) [A11](08_sources.md#a11) [P3](08_sources.md#p3)

**Решение для проекта:** учитывать использование в авторизации и не доверять payload только после декодирования. Не ограничивать определение JWT утверждением «всегда три части»: RFC связывает представление с JWS/JWE. Предполагаемое истечение срока не отменяет необходимость отдельно оценить историческое раскрытие секретного материала. [A11](08_sources.md#a11)

## 9. Other high-entropy secrets

**Смысл:** оставшиеся секреты приложения, которые не отнесены к более определённой группе. Высокая энтропия — возможный признак для отбора, а не определение конфиденциальности.

**Подтверждённый пример:** Django `SECRET_KEY` используется для криптографической подписи и должен храниться в секрете. [A13](08_sources.md#a13)

**Решение для проекта:** требовать признаков секретного назначения. Случайный идентификатор, checksum или Git object ID не должен становиться положительным примером только из-за внешней случайности. Название категории не обязывает вводить один универсальный порог энтропии; такого порога в roadmap нет. [P0](08_sources.md#p0) [P3](08_sources.md#p3)

## Пересечения категорий и смысл меток

Предлагается оставить бинарную задачу «секрет / не-секрет» основной, а категории использовать для разметки, анализа ошибок и отчёта. Это согласуется с запланированной классификацией кандидатов, но не означает, что уже утверждён отдельный девятиклассовый классификатор. [P0](08_sources.md#p0)

Схема для согласования: `label = SECRET | NON_SECRET | UNCERTAIN`, `primary_type`, дополнительные теги, исходная метка датасета, происхождение, обоснование разметки и `activity_status = UNKNOWN`. Первые варианты этой схемы уже были предложены в `examples_leaks.md`; здесь она не объявляется окончательно утверждённой. [P3](08_sources.md#p3)

В первую очередь сохранить семантику источника. Например, метки и правила CredData нельзя механически приравнять к нашей `UNCERTAIN` или `NON_SECRET`: у источника есть собственные условия, включая тестовые credentials. [A06](08_sources.md#a06)

На следующем этапе нужно утвердить приоритет категорий, учёт составных credentials и отображение меток каждого набора. В этом пакете не созданы секреты, обучающие строки или искусственная разметка несуществующих находок.
