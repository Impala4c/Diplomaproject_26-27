# Критерии оценки и проект протокола

**Статус:** критерии будущего эксперимента, подготовленные на этапе постановки. Метрики ещё не измерены. Roadmap требует precision, recall, F1, ложные срабатывания, время, анализ по категориям, находкам только в истории и полноте извлечения. [P0](08_sources.md#p0)

## 1. Три разных уровня оценки

**Исторический сбор.** Проверить, что коллектор получил именно заявленные refs и нужные версии файлов. На контролируемых историях перечень ожидаемых объектов и мест известен заранее. Потери на этом уровне не следует скрывать последующей успешной классификацией нескольких строк.

**Извлечение кандидатов.** Оценить, какая часть известных секретных фрагментов вообще вошла в множество кандидатов до ML.

**Полный конвейер.** Оценить окончательные предупреждения после извлечения, классификации и нормализации. Если положительный объект пропущен извлечением, он остаётся пропуском полного конвейера, даже если классификатор его не видел.

Раздельная оценка извлечения и итогового метода предусмотрена roadmap. Разделение на эти три уровня — предлагаемая детализация протокола. [P0](08_sources.md#p0)

## 2. Единица учёта — предложение на согласование

Для основного сравнения предлагается учитывать уникальное место секретного фрагмента: репозиторий, файловый объект, путь и диапазон секретного материала. Список коммитов, в которых это место присутствует, хранится как происхождение, а не автоматически как множество новых независимых находок.

Отдельно сообщать количество уникальных значений по безопасным отпечаткам и количество появлений в истории. Полный блок private key не считать несколькими секретами по числу строк. Для составной строки подключения заранее определить, какое секретное поле является учитываемой единицей.

Это ещё не утверждённая схема разметки. До эксперимента необходимо согласовать правила для перемещения фрагмента, дубликатов, связанных AWS-компонентов и пересечений категорий. Метрики методов считаются только после одинаковой нормализации.

## 3. Эталонные метки и спорные случаи

В предыдущих материалах предложены `SECRET`, `NON_SECRET`, `UNCERTAIN`. `SECRET` не означает подтверждённые действующие credentials. [P3](08_sources.md#p3) [P0](08_sources.md#p0)

Предлагается независимо размечать двумя авторами, затем обсуждать расхождения с фиксацией решения. Подобная процедура двух разметчиков с обсуждением описана в SecretBench, но это не свидетельство уже выполненной разметки нашей командой. [S03](08_sources.md#s03)

Неоднозначные записи не превращать автоматически в отрицательные. Для основной бинарной оценки использовать только согласованную часть и явно показывать число исключённых/неразрешённых записей. Если не все предупреждения получили метку, precision относится только к проверенной части; рядом указывается доля проверенных предупреждений.

Для внешних наборов сохранять исходную метку отдельно от приведённой к нашей схеме. CredData имеет собственные правила для тестовых и примерных значений; соответствие классов нужно документировать, а не угадывать по буквам меток. [A06](08_sources.md#a06)

## 4. Метрики на фиксированном размеченном наборе

`TP` — секретные объекты, правильно отмеченные методом. `FP` — несекретные объекты, ошибочно отмеченные как секрет. `FN` — известные секреты, не отмеченные методом. `TN` — правильно отклонённые несекретные объекты внутри определённого конечного набора оценки.

```text
Precision = TP / (TP + FP)
Recall = TP / (TP + FN)
F1 = 2 × TP / (2 × TP + FP + FN)
FPR = FP / (FP + TN)
```

Определения precision, recall и F-меры приведены в документации scikit-learn. FPR требует заранее определённого множества отрицательных примеров; формула здесь записана через определённые выше счётчики. [A03](08_sources.md#a03)

**Не путать:** `FP / (TP + FP)` — доля ложных предупреждений среди выданных, равная `1 − precision`, а не FPR. Это следует непосредственно из формул.

Для end-to-end сканирования нельзя без определения отрицательной совокупности считать TN как «все остальные строки всех коммитов». Тогда результат зависел бы от искусственно выбранной единицы отрицательного наблюдения. Поэтому FPR предлагается использовать на фиксированном наборе кандидатов, а в сквозном отчёте обязательно давать FP и precision.

Нулевой знаменатель не заменять произвольным «100%». При отсутствии положительных примеров recall категории не определён; при отсутствии предупреждений precision не определён. Политику отображения `N/A` и параметры расчёта зафиксировать; scikit-learn отдельно документирует такие случаи. [A03](08_sources.md#a03)

## 5. Полнота извлечения и исторический срез

Пусть `G` — множество известных положительных единиц эталона, а `C` — кандидаты до ML, сопоставленные с эталоном по общему правилу.

```text
Recall_extraction = количество элементов G, найденных в C / |G|
Recall_end_to_end = количество элементов G в итоговом отчёте / |G|
```

Если классификатор только фильтрует `C`, а не создаёт новые кандидаты, то `Recall_end_to_end <= Recall_extraction`. Это свойство данной конструкции конвейера, а не измеренный результат.

Отдельно определить `G_history_only`: известные секреты, присутствующие в полученной истории и отсутствующие в выбранном текущем снимке. Для него сообщать собственную полноту, размер множества и SHA снимка. Смысл сравнения с текущим состоянием соответствует задаче roadmap. [P0](08_sources.md#p0)

На собственных историях `G` задаётся при подготовке теста. На независимом benchmark метрика относится к его известной разметке и охвату, не ко всем потенциально неизвестным секретам проекта. Если полного эталона нет, общий recall произвольного публичного репозитория не заявляется.

## 6. Как сравнивать методы

В обязательном плане: собственные правила, Gitleaks и TruffleHog, затем Logistic Regression и Random Forest с проверкой TF-IDF-контекста. [P0](08_sources.md#p0)

Для сравнения вариантов **с контекстом / без контекста** оставить одинаковыми исходные кандидаты, разбиение и семейство модели. Для сравнения **с внешними инструментами** дополнительно выровнять доступные версии файлов, области исключений и единицу находки.

Предлагаемый набор вариантов: правила без ML; числовые признаки без контекста; те же признаки плюс контекст; внешние baseline отдельно. Не требуется заранее объявлять любую из этих строк победителем.

Внешние сканеры могут формировать результаты в отличающихся форматах. До оценки нужно описать адаптер сопоставления: место секрета, границы фрагмента, повторные предупреждения, многострочные блоки. Иначе различие форматов может ошибочно выглядеть различием качества.

## 7. Разделение данных и выбор параметров

Roadmap требует разделять связанные репозитории и дубликаты; преобразования обучать только на train, пороги выбирать на validation. [P0](08_sources.md#p0)

Документация scikit-learn объясняет риск утечки информации через preprocessing и использование групп для связанных наблюдений. [A04](08_sources.md#a04) [A05](08_sources.md#a05)

Предлагается до разбиения определить группы связанных репозиториев, форков, повторов секретов и общих шаблонов. Такие группы не должны пересекать train/validation/test. Конкретные доли частей и random seed в материалах не заданы; здесь они не выдуманы.

Сохранять происхождение данных. Внешний датасет не становится независимым test set только из-за другого названия: нужно проверить пересечения с обучающими данными. Синтетические и независимые данные оцениваются раздельно по требованию roadmap. [P0](08_sources.md#p0)

## 8. Проверка гипотезы о контексте

Основной критерий предложен в `02_questions_hypothesis.md`: уменьшение FP при `R_context >= R_without_context − epsilon`. Значение `epsilon` должно быть согласовано до итогового test set.

После выбора по validation параметры фиксируются. На test не корректировать порог, категории и фильтры в поисках желаемого результата. Отдельно показывать, насколько изменились обе величины — FP и recall. При нулевом FP у сравниваемого baseline относительное процентное снижение не вычислять делением на ноль.

Одного положительного различия недостаточно для вывода о статистической значимости. План оценки неопределённости и достаточности выборки нужно согласовать отдельно; тест значимости в этом этапе не выполнялся.

## 9. Категории и время работы

Общая бинарная метрика считается по единому набору единиц, без повторного счёта пересекающихся категорий. Для анализа ошибок показывать support категории, TP/FN и относимые к ней FP по заранее описанному правилу. Если отрицательные примеры по категориям не распределены, не публиковать видимость полноценного category-level FPR.

Для времени предлагается отделять получение репозитория, локальное извлечение, вычисление признаков и inference. Время обучения сообщать отдельно. Записывать окружение, объём обработанных данных, исключения и число повторных запусков. Ни аппаратные характеристики, ни длительность в этом пакете не угаданы.
