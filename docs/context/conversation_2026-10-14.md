## 12. Ассистент

Предлагаю начать с **локального сканера истории одного Git-репозитория**. Его первая задача — показать, что удаление секрета из текущего файла не убирает его из истории.

Программа будет работать так:

1. Получает путь к локальному тестовому репозиторию.
2. Читает коммиты и версии файлов в истории основной ветки, включая первый коммит.
3. Ищет секреты одной выбранной категории.
4. Выдаёт находки: коммит, путь к файлу, диапазон строк, категорию и замаскированное значение.

Для первой демонстрации подготовим историю из трёх коммитов: обычный файл → добавление искусственного секрета → удаление секрета. На последнем коммите файл уже чистый, но сканер должен показать историческую находку. Так мы проверим весь путь от чтения Git до результата.

Первой категорией предлагаю взять **AWS credentials**, а внутри неё — только пару `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`. Это соответствует вашему запланированному направлению AWS-сценариев и позволяет начать с понятного контекста: два связанных поля конфигурации.

Для первой версии установим узкое правило: ищем эти поля в одном файле формата `.env`. Один идентификатор доступа без секретного компонента не считаем полной парой. Все значения для демонстрации будут искусственными; программа только читает файлы, без проверки доступа к AWS.

Минимальные случаи для проверки:

| Ситуация | Ожидаемое поведение |
|---|---|
| В историческом файле есть заполненная пара | Показать находку |
| Пара удалена в следующем коммите | Сохранить историческую находку |
| Есть только `AWS_ACCESS_KEY_ID` | Не считать полной парой |
| Оба поля пустые | Не показывать находку |
| Одна версия файла встречается в нескольких коммитах | Не перечитывать содержимое, сохранить связи с коммитами |

**ML на этом шаге ещё не нужен:** сначала проверяем чтение истории, извлечение и отчёт. Позже этот же конвейер будет передавать кандидатов классификатору.

Такой объём кажется подходящим для первого работающего результата. Тебе ближе начать с AWS-пары или хочется сначала обсудить альтернативу — например, закрытые ключи?

## 15. Ассистент

Берём AWS-пару. **Программа будет искать потенциально раскрытые credentials, но не сможет подтвердить, что они действуют.** Правдоподобный искусственный пример может выглядеть точно так же, как настоящий ключ. Поэтому кроме обнаружения нам понадобится оценка контекста и статус «неоднозначно».

У AWS долговременный ключ доступа состоит из идентификатора и секретной части. Для временных credentials нужен ещё session token — их полный разбор предлагаю оставить на следующий этап. [Документация AWS](https://docs.aws.amazon.com/IAM/latest/UserGuide/securing_access-keys.html)

**Как будет идти поиск**

Для первой версии предлагаю следующий порядок:

1. **Прочитать историю выбранной ветки.** Программа получает путь к локальному репозиторию и читает сохранённые версии файлов, включая удалённые из текущего состояния. Переключать рабочую папку между коммитами не требуется.
2. **Выбрать файлы семейства `.env`.** Например, `.env`, `.env.production`, `.env.example`. Файлы с `example` тоже проверяем: название само по себе ничего не гарантирует.
3. **Найти присваивания двум полям:** `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`. Учесть пробелы, кавычки и необязательный `export`.
4. **Извлечь значения и связать их.** В простом случае в одной версии файла есть ровно одно присваивание каждому полю — считаем их предполагаемой парой. Между разными коммитами или файлами значения не склеиваем. Если присваиваний несколько, отмечаем неоднозначность.
5. **Оценить значения и контекст.** Проверить пустые значения, подстановки переменных, явные заглушки, соответствие ожидаемому формату и окружающие пояснения.
6. **Сформировать маскированный отчёт.** Указать место, статус и причину решения.

Если одна версия файла повторяется в нескольких коммитах, содержимое достаточно разобрать один раз, сохранив сведения о её появлениях.

**Как отличать пример от подозрительной пары**

Предлагаю такие правила первой версии. Это наш проектный выбор, который затем проверим на тестах:

| Что находится в файле | Решение | Почему |
|---|---|---|
| Оба значения пустые | Пустая конфигурация | Секретные значения отсутствуют |
| `your_access_key_here` и `your_secret_key_here` | Явная заглушка | Есть конкретные признаки шаблона |
| `${AWS_ACCESS_KEY_ID}` и `${AWS_SECRET_ACCESS_KEY}` | Ссылка на переменные | Самих значений в этих строках нет |
| Точная известная пара из документации AWS | Известный учебный пример | Совпадает с заранее зарегистрированным примером |
| Два конкретных значения ожидаемого формата | Подозрительная пара | В файле явно записан материал, похожий на credentials |
| Такая же пара в `.env.example` или рядом с комментарием `test` | Подозрительная либо неоднозначная | Имя файла и комментарий не доказывают искусственное происхождение |
| Только идентификатор | Неполный кандидат | Секретный компонент не найден |
| Только секретная часть | Отдельный подозрительный компонент | Полной пары нет, но потенциально чувствительное значение нельзя терять |

AWS публикует демонстрационную пару в документации. Для её распознавания нужно сравнивать **точные значения**, а не исключать всё, где встретилось слово `EXAMPLE`. [Пример AWS](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_access-keys.html)

Здесь уточню прежнее предложение: отсутствие полной пары не должно означать, что программа молча отбрасывает секретную часть. В отчёте можно отдельно показывать **пары** и **неполные кандидаты**.

**Что даёт контекст**

Имя поля помогает понять назначение строки. Расположение двух полей в одном файле помогает предположить связь. Комментарии, путь и соседние строки дают дополнительные признаки.

Но правило «лежит в тестах — значит безопасно» будет ошибочным. Аналогично, высокая энтропия — то есть внешняя случайность строки — не доказывает секретность: случайный учебный пример тоже может иметь высокую энтропию.

Поэтому на первом этапе лучше выдавать объяснимое решение:

> Подозрительная AWS-пара: оба поля содержат конкретные значения ожидаемого формата; явные заглушки не обнаружены. Действительность не проверялась.

Без выдуманного «вероятность утечки — 97 %».

**Как проверим это на своих примерах**

Нам понадобятся два разных типа искусственных данных:

- **Очевидные заглушки** — программа должна распознавать их как шаблон.
- **Правдоподобная синтетическая пара** — программа должна обнаруживать её как подозрительную.

Во втором случае мы знаем, что пара искусственная, потому что сами подготовили тест. Сканер не должен получать эту подсказку: иначе демонстрация ничего не проверит. Такой тест подтвердит поиск в истории и работу правил, но ещё не способность отличать реальные утечки от всех учебных примеров.

Итог минимальной версии — найти пару после её удаления, показать происхождение, объяснить решение и скрыть значения в отчёте. Всё это пока обсуждаем; ничего не создаю.

## 18. Ассистент

**ML подключим после извлечения кандидатов.** Уже сделанный поиск по истории останется основой: модель будет оценивать найденную AWS-пару вместе с её контекстом.

```text
Git-история → кандидаты AWS → признаки → правила или ML → отчёт
```

Так можно будет сравнить два варианта на одинаковых находках: решения по правилам и решения модели. Если извлекатель вообще не обнаружил значение, ML на следующем этапе его уже не восстановит.

**Что будет получать модель**

Один обучающий пример — предполагаемая AWS-пара в конкретной версии файла, окружающий контекст и эталонная метка.

| Группа признаков | Примеры |
|---|---|
| Свойства значений | Длина, состав символов, энтропия, соответствие формату |
| Связь компонентов | Есть ли оба поля, расстояние между ними, повторные присваивания |
| Окружающий текст | Имена переменных, комментарии, соседние строки |
| Контекст файла | Расширение, признаки конфигурации, документации или тестового файла |

Сами значения в текстовом контексте предлагаю заменять маркерами вроде `<ACCESS_KEY_ID>` и `<SECRET_VALUE>`, а их числовые характеристики считать отдельно. Это уменьшит возможность запоминания конкретных ключей.

Первой моделью предлагаю **Logistic Regression с числовыми признаками и TF-IDF контекста**. Затем сравним с Random Forest, предусмотренным вашим планом. Модель будет обучаться отдельно и сохраняться; обычный запуск сканера будет только применять её.

**На каких данных обучать**

Нам нужны три источника с разными назначениями:

| Источник | Для чего используем |
|---|---|
| Собственные синтетические Git-истории | Проверяем поиск, удаление, повторение, связывание пары и отчёт |
| CredData | Рассматриваем как первоначальный источник размеченных кандидатов и контекста |
| SecretBench | Рассматриваем как дополнительный источник после получения доступа |

**CredData** содержит вручную размеченные строки и исходный контекст, но значения и пути преобразованы. Есть существенный нюанс: AWS-значения могут заменяться демонстрационными, а credentials в тестовых каталогах по правилам набора могут иметь положительную метку. Поэтому нельзя автоматически считать «примерное значение» отрицательным или переносить все метки без проверки. [Описание CredData](https://github.com/Samsung/CredData)

**SecretBench** содержит размеченные кандидаты из публичных репозиториев. Доступ к чувствительным данным предусматривает обращение к авторам и соглашение об их защите; сейчас доступ вашей команды не подтверждён. [Описание SecretBench](https://github.com/setu1421/SecretBench)

Оба набора **не являются готовой таблицей AWS-пар для нашего узкого `.env`-сканера**. Сначала потребуется проверить, сколько там подходящих записей, сохранились ли оба компонента и достаточно ли независимых примеров. Если их мало, придётся расширять поддерживаемые форматы либо откладывать выводы о качестве AWS-модели.

**Чему именно будем учить**

Здесь нужно точнее сформулировать цель: модель учится распознавать **секретный материал по принятой политике разметки**, а не действующий доступ к AWS.

Предлагаю три статуса разметки:

- `SECRET` — материал признан секретным по контексту и основаниям разметки; действительность не проверяется.
- `NON_SECRET` — явная заглушка, подстановка переменной, документированный учебный пример или другое несекретное значение.
- `UNCERTAIN` — оснований недостаточно. Такие записи сначала разбираем отдельно и не заставляем модель учиться на случайном ответе.

Вы вдвоём независимо размечаете выбранные записи, затем обсуждаете расхождения. Исходную метку датасета сохраняем отдельно от вашей итоговой метки.

**Нельзя обучать модель только на «случайная строка = секрет, слово `example` = не секрет».** Она выучит этот простой трюк. Нужны сложные отрицательные примеры, похожие на credentials, и положительные примеры в разных контекстах. Правдоподобные синтетические пары при этом остаются отдельными тестовыми данными: нельзя объявлять их реальными утечками ради обучения.

**Как проверим пользу ML**

Разделим данные на обучение, подбор параметров и финальный тест **по семействам репозиториев и дубликатов**. Одна пара из десяти коммитов не должна оказаться одновременно в обучении и тесте.

На одинаковом разбиении сравним:

1. Правила без ML.
2. Модель только со свойствами значений.
3. Такую же модель с добавлением контекста.

Проверим, уменьшились ли ложные срабатывания и сколько секретов при этом пропущено. Допустимое снижение полноты согласуем до финального теста.

Для нашего текущего шага достаточно предусмотреть, чтобы поиск сохранял **кандидата, его происхождение и контекст до окончательной фильтрации**. Это позволит позже подключить ML без переписывания коллектора. Ничего пока не создаю.

## 28. Ассистент

Это проверяется **уже существующими модульными тестами**. Наш демонстрационный репозиторий проверяет поиск удалённой пары, а эти тесты — решения для разных значений.

В PowerShell из папки проекта выполни:

```powershell
python -B -m unittest tests.unit.test_aws -v
```

Эта команда не создаёт новые репозитории или отчёты. Ожидаемый итог:

```text
Ran 15 tests ...
OK
```

Перед итогом у каждого теста должно стоять `ok`.

**Что именно проверяется:**

| Входные данные | Ожидаемое решение |
|---|---|
| Оба поля пустые | `NON_SECRET` |
| `your_access_key_here` и `your_secret_key_here` | `NON_SECRET` |
| `${ACCESS_ID}` и `$SECRET_VALUE` | `NON_SECRET`: ссылки на переменные |
| Точная публичная пара из документации AWS | `NON_SECRET`: известный пример |
| Искусственная пара правдоподобного формата | `SUSPECTED_SECRET` |
| Только идентификатор | `INCOMPLETE` |
| Только правдоподобная секретная часть | `SUSPECTED_SECRET` |
| Повторные присваивания полям | `UNCERTAIN` |

Например, тест `test_exact_public_example` проверяет распознавание известного примера AWS, а `test_example_word_is_not_an_allowlist` — что наличие слова `EXAMPLE` не заставляет программу автоматически пропустить другую пару.

Можно запустить только проверку заглушек:

```powershell
python -B -m unittest tests.unit.test_aws.AwsRulesTests.test_placeholders_empty_and_environment_references -v
```

**Важная граница:** сейчас программа отличает очевидные заглушки и конкретный известный пример по правилам. Она не умеет достоверно отличить любой выдуманный ключ от настоящего. Если учебная пара полностью похожа на реальные credentials, предупреждение о ней ожидаемо. `OK` подтверждает соблюдение наших правил, а не безошибочное распознавание всех утечек.
